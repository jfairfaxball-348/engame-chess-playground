# S010 — Chess AI research and architecture workshop
**Reviewed:** 2026-10-23 | **Status:** reconnaissance, not a validated engine improvement | **Scope:** independent experimental Engine Playground only

## Executive conclusion

**Feasible now:** use native Stockfish/Lc0/UCI engines as local opponents; ingest PV, score, node and timing telemetry; collect reproducible positions and games; train small supervised goal/value models; run modest search and goal-conditioned experiments. **Not justified yet:** building eight cooperating specialists or attempting frontier-scale self-play on an unmeasured laptop. **Potential research direction:** an opponent-resistant positional-goal reachability model that decides *whether to pursue, change or abandon* strategically useful goals, tested as a search aid against strong budget-matched baselines. This is a hypothesis, **not an established novelty or performance claim**.

The user supplied the requirements for S010, superseding prior claims that *all* research was out of scope. Existing restrictions remain absolute for the Maths Endgame mode and the independent theorem repository. No experiment may silently alter or unlock the proof-derived mode.

## 1. Native integration: choose the transport, not an engine-specific API

| Option | Operational model | Advantage | Risk / verdict |
|---|---|---|---|
| **A. HTTPS Vercel page → localhost companion** | Browser explicitly connects to \`127.0.0.1\` companion over local WebSocket (or HTTP for commands); companion spawns whitelisted native UCI subprocesses | Preserves hosted UI, local compute, per-line streaming \`info\`; **first browser spike** | Browser-specific Local Network Access (LNA) prompts, mixed-content exceptions and other browsers' policies require real testing |
| **B. Entire UI served from localhost** | One native Python/Node service serves identical built frontend and engine API on same origin | Most portable/reliable local fallback; avoids cross-origin, public-to-loopback access | Hosted Vercel UI not the connection origin; local launch needed |
| **C. Companion makes outgoing authenticated WSS connection to a relay** | Local daemon dials out to persistent server; hosted site joins authenticated session | Remote/mobile spectator capability, no inbound port | Relay hosting, identity, privacy, latency, operational cost; **defer** |
| **D. Browser extension / Native Messaging** | Installed browser extension communicates with approved native host | Controlled browser integration | Deployment and support cost; **defer** |
| **E. Vercel API endpoint spawns local engine** | Not applicable | None | Vercel cloud functions cannot access processes on the user's laptop or substitute for a long-lived local worker |

**Web safety reality (as of October 2026):** An HTTPS page cannot assume ordinary access to \`localhost\`. Chrome's LNA framework (introduced in Chrome 142, October 2025) requires a user-granted \`loopback-network\` permission for public → loopback requests. Google's current browser guidance describes an exception allowing \`ws://127.0.0.1:PORT\` from HTTPS when the hostname is syntactically loopback, subject to the LNA permission. Fetch to local HTTP should declare \`targetAddressSpace: 'loopback'\` where supported. Old Private Network Access preflight headers are **not** the current Chrome permission mechanism. Firefox and Safari may behave differently; MDN's general mixed-content guidance is more restrictive. **This is documented behavior, not evidence of a successful Vercel-to-loopback test on the user's browser**. Test A in Chrome/Edge and Firefox; implement B if A is unreliable. Sources: [Chrome launch note, 2025-06-09; updated 2025-09-29](https://developer.chrome.com/blog/local-network-access), [GoogleChrome implementation guide, retrieved 2026-10-23](https://github.com/GoogleChrome/modern-web-guidance/blob/main/skills/modern-web-guidance/guides/security/local-network-access.md), [MDN WebSockets security](https://developer.mozilla.org/en-US/docs/Web/API/WebSockets_API/Writing_WebSocket_client_applications).

**Companion security requirements:** bind only to loopback; reject invalid \`Origin\` at WebSocket upgrade (WebSockets are **not protected by CORS**), and CORS-allowlist the exact hosted origin for HTTP; require unpredictable per-session bearer authentication / handshake token, explicit connect UI and user consent. Do not spawn executable paths supplied by the website: only launch explicitly registered local binaries with controlled arguments and working directories, resource caps and kill-on-disconnect. Reject arbitrary UCI options with path/file implications; rate-limit connections and messages; cap logs; no \`0.0.0.0\` binding; never relay local engine credentials/filenames. Plan for CSRF, DNS rebinding, reconnect, browser sleep, process crashes, cancellation and stale move IDs. Never expose engine telemetry to other website visitors. Authentication is needed even on loopback, not just CORS.

**Engine registry** lives on companion, not in a hardcoded frontend bundle. \`GET /v1/engines\` returns opaque engine IDs, display names, engine protocol and optional safe capabilities (MultiPV, threads, network requirement), not executable paths. \`POST /v1/sessions\` creates one engine instance per needed side (or more for analysis). \`WS /v1/sessions/{id}/stream\` emits \`ready\`, \`info\`, \`bestmove\`, \`error\`, \`stopped\`, each tagged with monotonically increasing \`request_id\` and \`position_id\`. Example request: \`{type:"analyse",position_id:"...",fen:"...",moves:[],limits:{movetime_ms:1000,multipv:3}}\`. Enforce legal FEN/move history, caller-selected limits, timeouts and session ownership. Return raw UCI fields *and* normalized White-perspective score, mate, PV UCI moves, depth, seldepth, nodes, nps, hashfull, multipv, time. \`position fen\` is fine for display, but game **history** must also be preserved for repetition/50-move analysis. Prefer \`python-chess\` as a reference UCI orchestration/legality adapter rather than writing all engine subprocess semantics ourselves ([project](https://github.com/niklasf/python-chess), [engine API](https://github.com/niklasf/python-chess/blob/master/docs/engine.rst)). UCI does **not** standardize model internals or reliable internal calculation introspection; PV/evaluation/time are what compliant engines generally reveal. A Python experimental engine can implement UCI and be launched exactly like native engines; non-UCI agents need a thin adapter.

**Suggested executable stack, provisional:** Python 3.11+/FastAPI or aiohttp + python-chess + asyncio subprocesses on the Windows host; native Stockfish 19, Lc0 with appropriate network and backend; optional PyTorch workers behind same API. Keep Vercel frontend static. Separate the protocol layer from browser presentation and training jobs; never run heavy training in the webserver request handler. Pin binary versions and network hashes. Check Lc0 network availability and CPU-only fallback, not simply whether its binary starts. Native UCI licenses and model/asset terms must be reviewed before redistributing bundled binaries.

## 2. Prior-art audit (primary sources; not an exhaustive systematic review)

| Work (publication) | What it already establishes | Implication for originality |
|---|---|---|
| **AlphaZero**, Silver et al., *Science*, **2018-12-07**, [paper](https://doi.org/10.1126/science.aar6404) | Strong chess through self-play, policy/value learning and MCTS | Self-play, neural policies and search integration are **established** |
| **Leela Chess Zero**, [implementation](https://github.com/LeelaChessZero/lc0), [training overview](https://lczero.org/dev/overview/) (ongoing) | Open-source UCI neural search and distributed self-play/training | Reusing Lc0 is sound engineering, not a novel learning architecture |
| **Stockfish NNUE**, [technical documentation](https://official-stockfish.github.io/docs/nnue-pytorch-wiki/docs/nnue.html), [trainer](https://github.com/official-stockfish/nnue-pytorch); **Stockfish 19 released 2026-09-05** ([announcement](https://stockfishchess.org/blog/2026/stockfish-19/)) | Efficient updatable learned evaluation integrated with high-performance alpha-beta search; extensive training ecosystem | A neural component inside conventional search is already proven practical; full Stockfish != browser Lite |
| **Planning with Goal-Conditioned Policies**, Nasiriany et al., *NeurIPS*, **2019**, [paper](https://papers.nips.cc/paper/9623-planning-with-goal-conditioned-policies) | Planning over learned subgoal-reaching policies (not specifically chess) | Goal-conditioned hierarchical planning alone is **not novel** |
| **Checkmating One, by Using Many / M2CTS**, Helfenstein et al., first arXiv **2024-01-30**, [paper, later revision](https://arxiv.org/abs/2401.16852) | Chess-specific phase-specialist mixture-of-experts with MCTS; authors report up to **+122 Elo versus a single-network baseline** (not versus current Stockfish) | **Critical prior art:** generic chess MoE orchestration is already done |
| **Superior Computer Chess with MPC, RL and Rollout**, Gundawar, Li & Bertsekas, arXiv **2024-09-10**, [paper](https://arxiv.org/abs/2409.06477) | Wrapping existing chess engines in a planning/opponent-simulation controller; reported improvements over evaluator component | **Critical prior art:** orchestration of multiple engines and opponent modelling is not a fresh concept |
| **Mastering Board Games by External and Internal Planning with Language Models**, Schultz et al., **2024-12-04**, [DeepMind](https://deepmind.google/research/publications/139455/) | Search around learned models boosts chess and other games | External search around strategic learned models is established |
| **Mixture of Masters**, Frisoni et al., first arXiv **2026-02-04**, [paper](https://arxiv.org/abs/2602.04447) | Chess-specific sparse expert routing, here primarily player style/persona; authors report benefits versus their comparison models | Dynamic multi-expert chess routing is crowded; different notion of expertise does not guarantee novelty |
| **Chessformer: A Unified Architecture for Chess Modeling**, Monroe et al., arXiv **2026-05-18**, [paper](https://arxiv.org/abs/2605.19091), [ICLR 2026 proceedings](https://proceedings.iclr.cc/paper_files/paper/2026/hash/3d167db04a90885ad5208fe8b273668b-Abstract-Conference.html) | Square-token transformer with geometric attention; authors report >100 Elo improvement on an Lc0 integration plus human-move and interpretability gains | Strong warning against assuming bigger orchestration beats better representations/search |
| **Opponent Modeling via Subgoal Inference**, Yu et al., [OpenReview](https://openreview.net/forum?id=Lt6wO0oZ8k) (confirm final venue/date before citation in any paper); and **Model-Based Opponent Modeling**, Yu et al., arXiv **2021-08-04**, [paper](https://arxiv.org/abs/2108.01843) | Opponent intentions/subgoals and recursive opponent reasoning studied in multi-agent RL | Opponent-goal inference as a general mechanism is not new |
| **ChessArena**, Liu et al., *ACL 2026*, [paper](https://aclanthology.org/2026.acl-long.360/) | Chess as a testbed for training/evaluating strategic reasoning with supervised + RL fine-tuning | Language-model chess RL is active; avoid equating fluent planning text with competitive play |

Open-source foundations: [python-chess](https://github.com/niklasf/python-chess) for legality/UCI/PGN; [Lc0](https://github.com/LeelaChessZero/lc0) for neural search; [nnue-pytorch](https://github.com/official-stockfish/nnue-pytorch) for mature evaluation training; [dlchess](https://github.com/mcfarljm/dlchess) and [chess-alpha-zero](https://github.com/Zeta36/chess-alpha-zero) as educational self-play bases (check maintenance, dependencies, correctness before adopting). For formal claims, do **not** treat project README Elo, paper abstract Elo or tournament anecdote as independently verified.

**Negative novelty verdicts:** "train on self-play", "use a tactical specialist with a strategy specialist", "use Stockfish as an oracle", "phase experts", "a controller over two engines", "a transformer playing chess", "learn opponent behavior", "learn a subgoal policy" are insufficient as new contributions. **Potential gap, subject to deeper prior-art search:** a *calibrated, adversarial, cost-aware test of whether a chosen chess-specific positional objective is achievable*, used online to retain/abandon objectives and improve play at **fixed total compute**. If no strength gain, a well-controlled negative result may still teach us something but is unlikely by itself to constitute a major engine breakthrough. The ambition to challenge frontier engines is a long-run experimental aim, not a credible projected near-term outcome.

## 3. Alternative ML architectures — keep hypotheses competing

| Candidate | Building blocks | Attractive property | Main objection / decision |
|---|---|---|---|
| **A. Search-only controls and light reranking** | Native UCI search + small explicit objective scorer on MultiPV candidates | Cheapest scientific baseline and easiest ablations | Extra evaluation calls/timing may make it weaker. **First research experiment** |
| **B. Learned goal-feasibility head** | Encode \`state, goal, side, horizon\`; supervise an adversarial reachability/value distribution; use as a bounded search prior | Directly tests ability to *construct* targets despite resistance; compact and trainable | Target labels and correct adversarial counterplay are expensive; cannot rely on curated easy positions. **Leading hypothesis** |
| **C. Joint policy/value/goal model inside search** | One compact neural model with shared trunk; policy, value and optional goal heads | Much less invocation overhead than multi-process experts; proper end-to-end learning eventually possible | More complex training and tight engine integration. **Later if B adds value** |
| **D. Phase/feature mixture of experts** | Specialist nets for tactical, pawn, endgame, etc. with learned routing | Can exploit specialization and sparsity | M2CTS and related work anticipate it; routing latency and data fragmentation. **Not first** |
| **E. External strategic orchestrator** | Multiple engines/models, opponent simulator, tactical veto and learned objective arbitration | Most flexible research platform for planning questions | Easy to accidentally buy Elo with more total compute; 2024 MPC paper already close. **Experimental only** |

One viable subgoal definition is a predicate over positions, **not** a fully specified arrangement of every piece. Examples: obtain a *supported knight outpost* on designated squares, establish a *rook on an open seventh rank*, or create/stop a passed pawn without conceding a tactical loss. Scope goals by legal side, horizon, material, king safety and position context; compare position-relative achievable sets rather than rewarding any arbitrary goal. Use game reward (+1/0/-1) as the primary objective and goal attainment as an auxiliary/diagnostic reward, otherwise the agent will happily realize useless goals and lose.

For an explicit finite-horizon adversarial reachability label, define \`R_h(s,g)\` as success under *all* opponent responses up to a fixed horizon (or use a calibrated probability under defined opponent policies and label it **policy-dependent**, not minimax). If exact full minimax is infeasible, report bounded-depth/limited-opponent approximation and disagreement with stronger refutation search; never call it a proof. Train on targeted adversarially generated positions (positive, negative, and hard near-misses) plus holdout opening families, unseen goals and stronger adversaries. Estimate *goal abandonment* as a learned decision conditioned on expected game WDL and goal feasibility; failure to meet goal should not automatically penalize the agent for choosing the best chess move.

**Minimise losses** is not equivalent to maximise Elo. A draw-seeking agent can reduce losses while substantially reducing wins. Report separate loss rate, draw rate, win rate, expected match score, Elo and performance across opponent strengths; pre-register any asymmetric risk preferences.

| Scale | Without GPU | With suitable GPU | Storage/notes |
|---|---|---|---|
| Native Stockfish matches and CPU oracle labels | Realistic on most modern multi-core laptops; benchmark first | GPU unnecessary for Stockfish NNUE inference | PGN/FEN/scored positions can start at tens to hundreds of MB |
| Goal predicates, minimax toy targets, 1k–20k labeled positions | Realistic but target-search label cost can dominate | Useful but optional | Track exact engine version, FEN+history, seed, labels, PV and source split |
| Small supervised goal/value model | CPU possible with small networks and datasets | More convenient and faster | Checkpoints, training logs, dataset license and held-out objectives |
| Moderate batched neural self-play | Often too slow to learn competitive chess on CPU alone | GPU strongly preferable; Python movegen may be throughput bottleneck | Requires replay storage and careful batching |
| Train leading-edge Lc0 / AlphaZero-class challenger from scratch | Unrealistic expectation for one unknown laptop | A single consumer GPU still no reason to expect frontier parity | Large self-play generation and repeated model selection/tuning |

For comparison, the **official NNUE PyTorch trainer's current README** says GPU training needs at least **16 GB system RAM and 8 GB VRAM (tight)** and that *its full dataset recipe* can require **800+ GB**; those are trainer/dataset-specific requirements, **not** prerequisites for this workshop's smaller models: [nnue-pytorch README](https://github.com/official-stockfish/nnue-pytorch). Do not buy hardware until a recorded profile demonstrates whether the bottleneck is CPU move generation, engine search, GPU inference/training or I/O. Use local SSD, bounded job workers, data manifests/hashes and periodic checkpoints; install PyTorch in a separate virtual environment. Use CUDA if available, otherwise CPU; train and inference should be separate jobs/processes.

## 5. Scientific evaluation — strength is the final arbiter

**Harness:** [fastchess](https://github.com/Disservin/fastchess) or [cutechess](https://github.com/cutechess/cutechess) for UCI matches and PGNs; [OpenBench](https://github.com/AndyGrant/OpenBench) for future distributed SPRT/regression tests. Initial local runs should be simple, not a new tournament platform. [fastchess manual](https://github.com/Disservin/fastchess/blob/master/man.md). Independent rating lists or tournaments require repeatable broad strength, appropriate submission and third-party acceptance; no self-declared ratings.

- **Controls:** same executable/backend for base and variant; identical opening book positions, paired colour-swapped games, same threads/hash/ponder, same allowed time or **total** wall-clock/CPU/GPU resources including all specialists, same opponent, versioned models. Report peak RAM/GPU and aggregate time. Node count is useful **within comparable search architectures**, not equivalent across Stockfish/Lc0/transformers. Engine-search time consumed to construct goal labels must be distinguished from *online playing* time. Avoid leakage from data labelling to holdout.
- **Statistics:** report W/D/L, score, loss probability and uncertainty, Elo with confidence bounds, match pair variance, SPRT settings (alpha/beta and null/alternative) where appropriate. 50–100 games are smoke tests, not decisive proof of small Elo changes. Use multiple opponents and opening suites, fixed seeds, repeated train seeds and explicit no-improvement results. Treat changes in draw adjudication and book selection as confounders.
- **Ablations:** baseline Stockfish budget alone; equal-budget baseline + random goal; + static goal heuristic; + learned feasibility; + abandonment; + opponent-conditioned policy; + more compute without goal model. A model only "better" because it calls Stockfish more often is **not** a learning discovery.
- **Goal metrics:** per-goal achieve-by-H rate, *adversarially resisted* rate, false-positive feasibility, calibration/Brier score and holdout success at different opponent strengths. Also evaluate position WDL change, time cost and unseen pawn structures/position families. High target-achievement with inferior chess WDL = failure of the scientific playing-strength claim.
- **Reproducibility:** immutable commit, engine binary and network hash, dataset license/hash/split, training seed, hyperparameters, opening suite, time controls, hardware inventory, PGNs, commands, calibration outputs and raw match logs. Freeze benchmarks **before** looking at new test results.

## 6. Recommended first experiments and gates

**S011 — feasibility / integration (engineering prerequisite; not a strength claim).**
1. Collect Windows hardware inventory and benchmark baseline native Stockfish 19; install native Lc0 + a suitable network only if hardware permits useful inference. Confirm versions, license and actual throughput.
2. Build a minimal loopback-only companion with allowlisted UCI binaries (Stockfish plus a second UCI binary or a tiny Python fake-UCI fixture) and session authentication. Test Chrome Vercel HTTPS→loopback LNA/WebSocket from an explicit click; test denied permission, malicious Origin, missing token, mixed-content/error handling, restart and crash. Test Firefox and document fallback B (same-origin localhost UI).
3. Expose discovery and telemetry; two simultaneous independent engines, White/Black selection, legal moves, stream \`depth/time/nodes/score/PV\`, cancellation and reset. Pass a >=20-ply smoke match and repeatable negative security tests. Preserve every existing Maths Endgame gate and all current Engine Playground functions. No experimental training library in the endgame mode.

**S012 — first scientific experiment (only after measuring machine throughput).** Pre-register one chess-relevant goal predicate (e.g. supported knight outpost) and positional horizon. Construct balanced, tactical-filtered, position-family-disjoint train/validation/test sets; label *opponent-resistant* success under specified limited search rather than assuming an obliging opponent. Start with **200 held-out positions** and at least two adversary strengths; this is a diagnostic pilot, not an Elo proof. Compare: (1) static predicate baseline, (2) opponent-aware bounded reachability heuristic, (3) trained goal-conditioned feasibility model. Success criteria for the *pilot*: legal/consistent data and labels; measured calibration/goal-achievement lift against static baseline on unseen positions; no significant deterioration in assessed chess WDL. Then add as a **time-capped** reranker of MultiPV candidates; only promote if an adequately powered paired match versus a **budget-matched** baseline shows a positive point estimate, acceptable uncertainty, and no concealed compute inflation. No preset numerical Elo claim.

**Stop / pivot triggers:** browser loopback proves unreliable → local-first origin fallback; CPU neural inference dominates move search → abandon live multi-component inference; goal metric increases but match score falls → treat goal head as interpretability-only; no advantage against simpler heuristic at matched compute → return to representation/data/search profiling, not build more agents.

## Decision

**Build the experiment platform, not an eight-brain engine.** Start with native UCI bridge + hardware measurement and a single opponent-resistant positional-goal hypothesis; treat Stockfish/Lc0 as baselines/oracles and potential components, not the project's claimed original invention. Revisit model architecture, MoE and orchestrator **only after** measurable controlled evidence. Keep all S010 material in this file; no new governance tree, no changes to upstream endgame-chess, and no release of KRK.
